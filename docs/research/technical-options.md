# Technical options and recommended Foundation stack

Research snapshot: **2026-10-27**. Target: an offline, local-first **Fedora Linux desktop** application for Foundation V1. Other platforms are future considerations. This decision is a documented implementation direction; it does not authorize implementing or running a prototype during Foundation research.

## Recommendation

Choose a **Rust modular monolith, SQLite, Tauri 2, and a TypeScript/React frontend built with Vite**. Keep all authoritative content/history operations in Rust application services. The webview receives typed view data and calls narrowly scoped commands. Adopt a versioned Memoquill document model and a ProseMirror-based editor adapter; the editor's private representation must not become the public storage contract.

This balances offline storage and file handling, a replaceable UI, practical rich-content tooling, and future portability. It is an engineering judgement, not a measured performance result or a learning-science finding. Accessibility and Fedora packaging are release-blocking feasibility gates, not assumptions.

The inspected [Tauri release list](https://api.github.com/repos/tauri-apps/tauri/releases?per_page=20) contains stable-named `tauri-v2.12.5` and `tauri-cli-v2.12.4`, published 2026-10-21; their versions are independent. The application crate's [manifest](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.5/crates/tauri/Cargo.toml) confirms 2.12.5, and the [workspace manifest](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.5/Cargo.toml) declares Rust 1.90 and `Apache-2.0 OR MIT`. No packages were installed or lockfile created.

Tauri 3 was checked rather than ignored: its [migration guide](https://v3.tauri.app/start/migrate/from-tauri-2/) explicitly describes **3.0 Alpha**; the release list includes `tauri-v3.0.0-alpha.5`. Its [runtime documentation](https://v3.tauri.app/develop/webview-runtime/) describes a choice of system WRY or bundled CEF and different GTK integration. This could change the tradeoff later, but an alpha runtime expansion is insufficient evidence to prefer it for V1. GitHub's `prerelease` flag alone is unreliable here: the alpha-named release was returned with that flag false. Re-evaluate after a stable release and Fedora accessibility/package evidence.

## Desktop alternatives

| Option | Practical strengths | Costs and risks for this product | Decision |
| --- | --- | --- | --- |
| Rust + Tauri 2 + TypeScript | Rust owns transactions, imports, recovery, scheduling, and agent boundaries. Web UI tooling suits long text, media, source review, and extensible practice views. System webview avoids bundling a Chromium engine. | Fedora's WebKitGTK and its accessibility/rendering behaviour become part of the supported runtime. Rust/JS IPC and two ecosystems add effort. Web-editor IME/focus/clipboard behaviour must be tested in the actual packaged app. | Preferred, conditional on gates below. |
| Electron + TypeScript, with a separated service layer | Bundled Chromium gives more uniform browser APIs and access to its mature web editor ecosystem. Main/preload/renderer separation can preserve a constrained API. | Chromium/Node distribution and security updates are the application's responsibility; larger shipped runtime by construction. Renderer privileges, preload exposure, native SQLite modules, and packaging require care. Rust services add a bridge; rewriting services in Node changes the architecture cost. | First fallback if WebKitGTK blocks essential accessibility/editor workflows. |
| Rust + GTK4/libadwaita | Native Fedora/GNOME integration and standard widgets with an accessibility model; avoids embedding a browser for the primary UI. Rust core can remain useful. | Rich document editing, embedded source views, and editor plugins need more native-widget/custom integration effort. Libadwaita brings GNOME design conventions and library-version constraints. Future Windows/macOS polish is a separate project. | Strong alternative if native Fedora integration and standard-widget accessibility outweigh rich-web-editor needs. |
| Qt 6, with a C++/QML or carefully chosen Rust bridge | Mature cross-platform widgets, text facilities, and accessibility interfaces; credible outside GNOME. | C++/QML/Rust integration or a second backend language adds effort. Module-by-module LGPL/GPL/commercial terms and distribution obligations need review. A custom QML editor still needs accessibility testing. | Credible reserve choice, not the default for the present Rust/TypeScript direction. |

Official [Tauri process documentation](https://v2.tauri.app/concept/process-model/) puts global state and database connections in the core process and uses operating-system webviews; [runtime-version documentation](https://v2.tauri.app/reference/webview-versions/) warns that Linux webview versions vary by distribution. These architectural facts explain distribution differences. They do **not** prove a particular RSS, startup time, energy saving, or editing latency advantage.

Electron's [process model](https://www.electronjs.org/docs/latest/tutorial/process-model) separates main, renderer, and preload responsibilities. Its [support policy](https://www.electronjs.org/docs/latest/tutorial/electron-timelines) covers the three latest stable release lines, making a sustained upgrade budget necessary. The [accessibility guide](https://www.electronjs.org/docs/latest/tutorial/accessibility) supplies testing guidance, not a guarantee that arbitrary custom web controls are accessible.

[GTK4 accessibility documentation](https://docs.gtk.org/gtk4/section-accessibility.html) describes standard controls, `GtkAccessible`, and an AT-SPI backend on Linux. The [GTK 4.14 development note](https://blogs.gnome.org/gtk/2024/03/08/accessibility-improvements-in-gtk-4-14/) specifically discusses bridging WebKitGTK accessibility trees. This is evidence about that GTK capability, **not evidence that Tauri 2 uses GTK4 or that its complete accessible tree works**. [Qt's accessibility API](https://doc.qt.io/qt-6/qaccessible.html) similarly exposes AT-SPI and built-in widget interfaces; actual Wayland/Fedora behaviour still requires testing.

## Fedora packaging, accessibility, and updates

Tauri's [prerequisite guide](https://v2.tauri.app/start/prerequisites/) lists Fedora dependencies; Linux Tauri 2 relies on WebKitGTK 4.1. The [RPM guide](https://v2.tauri.app/distribute/rpm/) warns about native library/glibc compatibility and building against the oldest supported base with the required WebKitGTK. Do not assume an RPM built on a newer Fedora will run on older Fedora, or that an AppImage removes every host dependency.

For V1, prefer an ordinary **RPM with declared runtime dependencies**, tested on the explicitly supported Fedora release(s). Select the concrete Fedora baseline when implementation begins; this research does not silently promise all Fedora versions, immutable variants, or every desktop environment. Test the main GNOME/Wayland path and document any additional supported session. Flatpak is a later packaging comparison if isolation/portals or runtime consistency justify its maintenance cost; it is not a prerequisite for offline operation.

Keyboard navigation, visible focus, labels/roles, screen-reader announcements, reduced motion, contrast, text scaling, and IME behaviour belong in the first vertical slice. Verify the actual WebKitGTK → AT-SPI → Orca path, including rich text, modal dialogs, long lists, and source previews. Browser accessibility checks alone cannot establish native integration. Never declare accessibility complete from a working web demo.

Use the distribution/package update path initially. Tauri's [updater plugin](https://v2.tauri.app/plugin/updater/) requires update signatures, but plugin availability does not authorize an update service or solve package ownership, rollout, downgrade, and schema compatibility. A future updater needs a documented ownership model, signed artifacts, migration/backup tests, and a working offline/manual route. Core learning must never require a network check or successful update.

## Frontend and editor options

| Choice | Assessment | Foundation decision |
| --- | --- | --- |
| React + TypeScript + Vite | Explicit component/state model and a broad editor/component integration ecosystem. Requires discipline around state duplication, focus preservation, and render work. No SSR/server framework is needed for this desktop app. [Official introduction](https://react.dev/learn). | Default UI, with accessible HTML controls and a small component set. Team familiarity has not been measured and is not part of this recommendation's evidence. |
| Svelte + TypeScript + Vite | [Compiler-based components](https://svelte.dev/docs/svelte/overview) can reduce application boilerplate and integrate with plain-JS editors. This does not prove lower total desktop memory or engineering cost. | Reasonable substitution before UI implementation if the implementation team is materially more effective with it; keep the same Rust/services and document contracts. |
| Vanilla TypeScript / Web Components | Few framework commitments; straightforward for very small screens. More manual state/focus/editor lifecycle work as authoring, import review, and progress views grow. | Do not choose merely to minimize dependency count; an explicit maintenance benefit is needed. |

Use **ProseMirror as the editor foundation**, through a narrow adapter. Its [guide](https://prosemirror.net/docs/guide/) distinguishes document schema/state, transactions, and views; it is a toolkit, not a ready-made complete authoring application. The inspected [prosemirror-model 1.25.0 manifest](https://github.com/ProseMirror/prosemirror-model/blob/1.25.0/package.json) and [MIT license](https://github.com/ProseMirror/prosemirror-model/blob/1.25.0/LICENSE) provide a concrete permissive reference. This is an inspected version, not a claim it is the newest or the future dependency pin.

Start with paragraphs, headings, lists, links, emphasis, code, images/attachments, and typed practice blocks. Avoid a general page-builder/plugin platform. Implement accessible menus and input handling as application work; ProseMirror's license and features do not establish the accessibility of custom controls. A wrapper such as Tiptap may reduce integration effort, but evaluate exact open-source packages separately from hosted/commercial extensions before selecting it. No Tiptap package or paid extension is selected by this document.

The first authoring gate must check selection, undo/redo, paste sanitization, keyboard controls, screen-reader editing, non-Latin input, large documents, and deterministic serialization in WebKitGTK. A basic Markdown editor can be a consciously reduced authoring fallback; it cannot silently remove required structured practice or provenance features.

## Persisted content and search

**Use SQLite as the authoritative local store**, with a versioned Memoquill document JSON for authored/normalized editable content and relational tables for identities, links, activities, attempts, review events, scheduler projections, import jobs, and provenance. Store immutable original imported files separately under managed resource IDs, with hashes and transactional references. JSON remains validated against the application's schema; it is not permission to store every domain relationship in an opaque blob.

| Representation | Good at | Limitation and treatment |
| --- | --- | --- |
| Markdown | Portable prose/code, readable diffs, interoperable import/export. | Cannot faithfully express every activity, stable block ID, attachment relationship, or source anchor without conventions. Preserve original Markdown; provide deterministic conversion and an explicit loss report. |
| Application document JSON | Typed blocks, stable IDs, structured activities, source anchors, and controlled migrations. | Requires schema/version migration and readable exports. Keep the Memoquill schema independent of unversioned editor-internal JSON. |
| HTML | Display interchange and some imported rich text. | Active content, ambiguous normalization, and editor/browser differences. Sanitize for display; never use unrestricted imported HTML as authoritative executable UI. |
| Plain text | Fast indexing, fallback reading, and simple exports. | Loses structure and media; derive it from validated content and retain originals. |

The native archive should include a format manifest, content/schema versions, resources and hashes, and optional personal-history sections with clearly chosen scope. Exporting educational content must not accidentally export personal attempts. Whole-library recovery must include those attempts when explicitly requested.

Use **SQLite FTS5** for local lexical search before adding any embedding/vector service. The [official FTS5 reference](https://www.sqlite.org/fts5.html) documents tokenizers, ranking, phrase/prefix queries, external-content tables, and index maintenance. Start with Unicode-aware tokenization and a rebuildable text projection. Test English/Cyrillic, punctuation, code symbols, diacritics, mixed scripts, and short queries; Unicode support does not imply language-aware morphology or semantic relevance. Consider trigram indexing only for a demonstrated substring need and after measuring its storage/query cost.

If using external-content FTS tables, update them in the same transaction or with tested triggers; an index can become inconsistent with its content. Provide rebuild/consistency checks. Do not introduce a separate search daemon for V1. All SQL receives bound values; query-language operators need deliberate escaping/UX rather than string concatenation.

Decide WAL, durability, and connection settings explicitly during storage implementation. A copied live database file is not automatically a complete backup. The [SQLite online backup documentation](https://www.sqlite.org/backup.html) describes consistent snapshots and alternatives such as `VACUUM INTO`; select and test one together with resource manifests, migrations, crash interruption, disk-full behaviour, and restoration. No storage settings or backup implementation were tested in this research.

## Scheduler, documents, and external-agent dependencies

**Recall scheduler:** evaluate `fsrs` behind an internal adapter. The [6.6.2 manifest](https://github.com/open-spaced-repetition/fsrs-rs/blob/v6.6.2/Cargo.toml), [public API](https://github.com/open-spaced-repetition/fsrs-rs/blob/v6.6.2/src/lib.rs), and [schedule example](https://github.com/open-spaced-repetition/fsrs-rs/blob/v6.6.2/examples/schedule.rs) were inspected. Persist event inputs plus algorithm/parameter versions; keep the clock, due-date policy, queue policy, and resources under application control. Default parameters are a starting policy, not personalized proof. Fitting, simulation, and experimental cost/ADR are not required to operate offline or to ship the first recall flow. See [existing-applications.md](existing-applications.md) for the detailed reuse decision.

**PDF:** V1 should preserve original PDF bytes and provenance. A bounded born-digital text-extraction/read-only-viewing path is useful, subject to parser/runtime/security review; OCR, EPUB, arbitrary full-HTML import, and high-fidelity layout reconstruction are deferred. [PDF.js](https://mozilla.github.io/pdf.js/) is an official browser-based parsing/rendering candidate, not a selected unreviewed dependency. Measure the actual worker/viewer behaviour and accessibility in Fedora WebKitGTK before adoption. The editable Memoquill document is a derived learning artifact, not a replacement for the PDF. Never execute document scripts, macros, imported code, or active HTML.

**MCP:** keep an optional adapter outside the core domain. The official Rust SDK was inspected at commit [`cd88056ffdc97756fbd98e5a12bbeb41758f0ce8`](https://github.com/modelcontextprotocol/rust-sdk/tree/cd88056ffdc97756fbd98e5a12bbeb41758f0ce8): its [manifest](https://github.com/modelcontextprotocol/rust-sdk/blob/cd88056ffdc97756fbd98e5a12bbeb41758f0ce8/Cargo.toml) declares 3.8.0/Rust 1.88; its [README](https://github.com/modelcontextprotocol/rust-sdk/blob/cd88056ffdc97756fbd98e5a12bbeb41758f0ce8/README.md) claims stable protocol 2026-07-28 support and documents stdio and HTTP transports. This is stronger evidence than treating a historically unofficial crate as current. It is still an evolving protocol/SDK with migration cost: pin the adapter and verify actual client negotiation, schemas, cancellation, limits, and lifecycle before shipping. SDK presence does not implement application authorization. Use scoped typed services and reviewable proposals; no unrestricted database/filesystem access or unauthenticated HTTP endpoint. Core functionality remains available when MCP and every model provider are absent.

## Early feasibility gates and revisit criteria

These are **planned checks for the first authorized implementation milestone**, not completed experiments. Freeze fixtures, target machines, and product budgets before measuring; report environment, versions, cold/warm conditions, and failures. Never fill a comparison table with invented benchmark numbers.

| Gate | Evidence required before the stack is accepted for V1 | Decision if it fails |
| --- | --- | --- |
| Fedora runtime/package | Install the produced RPM on a clean supported Fedora system; open/import/study/export/recover with networking disabled; verify runtime dependency declarations, Wayland behaviour, and launch after a system update. | Fix a bounded packaging/configuration issue first. Reconsider Flatpak or another supported baseline if dependencies cannot be shipped reliably. |
| Accessibility | Keyboard-only and Orca/AT-SPI completion of library navigation, source reading, authoring, review, import proposal, and recovery; focus and announcements survive dialogs/editor transitions; usable zoom/contrast/IME. | If essential WebKitGTK behaviour remains blocked, compare the same small flow in Electron. Choose GTK4 if native widgets provide the better verified route for the accepted product scope. |
| Content/editor fidelity | Stable IDs, schema validation/migration, undo/redo, safe paste, deterministic JSON/Markdown conversion, source-anchor survival, and disclosed loss on non-representable imports. | Simplify the editor/feature surface or replace its adapter; never corrupt the canonical schema to match a widget. Change frontend framework only for demonstrated integration value. |
| Storage/recovery | A review transaction and content edit preserve independent history; interrupted import/migration and disk-full leave a recoverable state; backup restore verifies resource hashes and event counts. | Storage design remains incomplete. Do not compensate with mandatory cloud sync. |
| Search/resource budgets | Representative small/large libraries including Cyrillic, code, and attachments; measure startup, RSS, due-queue latency, indexing, search and editor responsiveness; cancellation keeps UI usable. | Optimize measured bottlenecks before replacing stack components. Add search infrastructure only if FTS5 fails documented retrieval requirements. |
| Scheduler/dependency | Reproducible golden cases for ratings/elapsed days, no-history defaults, day boundaries, long gaps, parameter changes, and replay across an explicit pinned crate/toolchain; no hidden optimizer/network requirement. | Keep the internal interface and stored events; revise dependency/policy rather than rewriting history. |
| MCP adapter | Conformance against named client/protocol revisions, least-privilege tool scopes, proposal/approval boundaries, pagination, cancellation, and startup with no listener/model provider. | Block the current Foundation V1 release until M6 passes, or explicitly revise the release scope. Optional means user activation; it does not permit silently omitting the essential integration. Core offline operation must remain usable while it is disabled. |

Revisit the shell choice when accessibility evidence, a stable Tauri 3 runtime, or supported Fedora packaging changes the measured result. Revisit the frontend only before significant UI investment or on a demonstrated editor/accessibility blocker. Revisit SQLite only for a concrete unsupported requirement, not speculative future scale. These criteria keep one actionable default while retaining recoverable boundaries.
